### Issuing programmatic access tokens

Enable **Issue credentials** to let the connector issue a Snowflake [programmatic access token](https://docs.snowflake.com/en/user-guide/programmatic-access-tokens) for an existing user, and revoke one it has issued. Issued tokens appear as **Programmatic access token** resources alongside the user they belong to once that resource type is enabled (see the note below).

**Issue credentials** and **Sync secrets** are independent. Enabling **Issue credentials** lets the connector mint and revoke programmatic access tokens, and nothing else; enabling **Sync secrets** inventories Snowflake secrets and RSA public keys without granting the ability to mint tokens. Existing programmatic access tokens are inventoried through the opt-in **Programmatic access token** resource type.

<Note>
**Inventorying programmatic access tokens requires a privilege on each user.** The **Programmatic access token** resource type is opt-in: enable it in C1 when you want existing tokens in your inventory. While it is enabled, the sync runs `SHOW USER PROGRAMMATIC ACCESS TOKENS FOR USER` for each user in the account, and Snowflake requires ownership of that user or the `MODIFY PROGRAMMATIC AUTHENTICATION METHODS` privilege on it. When the connector's role has neither, the sync fails with an error naming that user instead of silently dropping previously synced tokens — those tokens stay live in Snowflake, and C1 needs its records to keep offering revocation for them. Grant the privilege with `GRANT MODIFY PROGRAMMATIC AUTHENTICATION METHODS ON USER <name> TO ROLE <connector-role>` (or transfer ownership of the user) before enabling the type.
</Note>

Token lifetime is set by the requester. Snowflake accepts whole days only, and the connector rounds down so a token never outlives the requested expiry. The minimum is one day and the maximum is one year; when no expiry is requested the token lasts 15 days.

<Warning>
**Snowflake requires a network policy on the user before it will issue a programmatic access token.** If the target user has no network policy attached, Snowflake rejects the request with `Network Policy is required when creating a programmatic access token for user <name>`. Attach a network policy to the user (or set one at the account level) before issuing. Creating a network policy requires a role with `CREATE NETWORK POLICY` on the account, which is more than the connector's own role needs.
</Warning>

<Note>
**Service users must have a granted default role.** For a user of type `SERVICE`, `SERVICE_AGENT`, or `LEGACY_SERVICE`, the connector restricts the issued token to the user's `DEFAULT_ROLE`, and verifies that role is granted to the user when its own role can read the user's grants. If the user has no default role, issuance fails before any token is created. If the default role is not granted, issuance fails either on that check or on Snowflake's own rejection of the statement.
</Note>

<Note>
**License data is opt-in and requires an organization account.** License resources report the Snowflake edition (Standard, Enterprise, or Business Critical) and, for single-account organizations, the number of users as consumed seats. Reading it requires connecting with an account that can view organization-level details, so enable this capability only when that access is available.
</Note>

[This connector can sync secrets](/product/admin/inventory) and display them on the **Inventory** page, and can issue programmatic access tokens. Both are opt-in and configured separately.

[This connector syncs non-human identities](/product/admin/nhi) and displays them on the **Identities overview** dashboard.

### Connector actions

Connector actions are custom capabilities that extend C1 automations with app-specific operations.

| Automation step | Actions offered | How the target is selected |
|-----------------|-----------------|----------------------------|
| Account lifecycle action | `enable_user`, `disable_user` | The step's own target-account selector — either the account in context or a specific account. C1 resolves `user_id` from that account. |

Both actions accept the following fields:

| Action name | Additional fields | Description |
|-------------|-------------------|-------------|
| `enable_user` | `user_id` (string, required) | Reactivates a Snowflake user by setting `DISABLED = FALSE` |
| `disable_user` | `user_id` (string, required) | Deactivates a Snowflake user by setting `DISABLED = TRUE`. Reverse it with `enable_user` |

<Note>
**`enable_user`/`disable_user` require `MODIFY` on the target user.** These actions run as the connector's **Write Role**, which defaults to `USERADMIN`. If that role holds neither `MODIFY` nor `OWNERSHIP` on the target user, Snowflake rejects the statement with `Insufficient privileges to operate on user '<name>'. Your primary role USERADMIN must have MODIFY granted on USER <name>.` Grant the privilege with `GRANT MODIFY ON USER <name> TO ROLE <write role>`, which does not transfer ownership. To avoid granting the `USERADMIN` system role to the service account at all, set **Write Role** to a role of your own — see [Privileges required for provisioning](#privileges-required-for-provisioning).

This restriction stays hidden when the service account keeps Snowflake's default `DEFAULT_SECONDARY_ROLES = ALL`: a higher secondary role such as `ACCOUNTADMIN` remains active alongside the `USERADMIN` primary role and supplies the privilege. Accounts restricted to `USERADMIN` alone are the ones that hit it.

**`enable_user` does not clear an account lockout.** Snowflake can independently lock a user out after repeated failed logins (tracked via `SNOWFLAKE_LOCK`/`MINS_TO_UNLOCK`), separately from the `DISABLED` property these actions toggle. `enable_user` only clears `DISABLED` - a locked-out user stays locked, and the C1 resource still reports a disabled status (`details: "locked"`) until an administrator clears the lockout directly in Snowflake.
</Note>

## Gather Snowflake credentials 

Configuring the connector requires you to pass in credentials generated in Snowflake. Gather these credentials before you move on. 

<Tip>
**For best results, use a dedicated service account.** C1 will use the `DEFAULT_WAREHOUSE`, `DEFAULT_NAMESPACE`, and `DEFAULT_ROLE` properties of the user used for the integration. For this reason, we recommend creating a dedicated service account in Snowflake for integrating with C1 with these default user properties.

For what to grant that service account, see [Choose a privilege model](#choose-a-privilege-model) below. Do not grant `MANAGE GRANTS` by default — it is an account-wide privilege and the connector does not require it.
</Tip>

## Choose a privilege model

The connector supports two discovery paths. They differ only in *which Snowflake surface the connector reads inventory from*, and therefore in what has to be granted. Pick one before you configure the connector.

<Note>
**`MANAGE GRANTS` is not scoped to a warehouse or a namespace.** `GRANT MANAGE GRANTS ON ACCOUNT` is an account-level global privilege: Snowflake defines it as the ability to grant or revoke privileges on **any** object in the account as if the granting role owned it, and Snowflake's documentation notes that a role holding it can grant further privileges to itself. Earlier versions of this page described it as applying to "the default warehouse and namespace." That was incorrect. If your security review rejects a standing account-wide privilege, use the ACCOUNT_USAGE model below, which needs no `MANAGE GRANTS` anywhere.
</Note>

### Model A: ACCOUNT_USAGE discovery (recommended for least privilege)

Set **Discovery Mode** to `account_usage`. The connector then reads inventory from the `SNOWFLAKE.ACCOUNT_USAGE` schema, which is account-wide by construction and gated by two database roles instead of by per-object grants.

```sql
USE ROLE ACCOUNTADMIN;

CREATE ROLE IF NOT EXISTS C1_CONNECTOR;
GRANT ROLE C1_CONNECTOR TO USER <service account>;

-- Users, roles, and role grants.
GRANT DATABASE ROLE SNOWFLAKE.SECURITY_VIEWER TO ROLE C1_CONNECTOR;
-- Databases, schemas, tables, and object grants. Omit this if you disable
-- "Sync databases and tables" (see Model C).
GRANT DATABASE ROLE SNOWFLAKE.OBJECT_VIEWER TO ROLE C1_CONNECTOR;

-- ACCOUNT_USAGE reads are SELECT statements, so they need compute. The SHOW
-- commands used by Model B are metadata-only and need no warehouse.
GRANT USAGE ON WAREHOUSE <warehouse> TO ROLE C1_CONNECTOR;
ALTER USER <service account> SET DEFAULT_WAREHOUSE = '<warehouse>', DEFAULT_ROLE = 'C1_CONNECTOR';
```

Trade-offs, both documented by Snowflake:

- **Latency.** `ACCOUNT_USAGE` views lag the live account by roughly 90 minutes to 3 hours depending on the view, so a sync reflects a slightly stale account. Model B is live.
- **A running warehouse.** The connector issues `SELECT` statements on this path, so the service account needs `USAGE` on a warehouse that can resume.

Integrations and RSA public key last-set timestamps have no `ACCOUNT_USAGE` equivalent and stay on the `SHOW`/`DESCRIBE` path in both models. Programmatic access tokens and Snowflake secrets likewise.

### Model B: SHOW discovery with per-user ownership

Leave **Discovery Mode** at the default `show`. Every `SHOW` command returns only the objects the session role holds at least one privilege on, so visibility has to be granted object by object. This still avoids `MANAGE GRANTS`, but role discovery covers only the roles explicitly handed to the connector rather than the whole account.

```sql
USE ROLE ACCOUNTADMIN;

CREATE ROLE IF NOT EXISTS C1_CONNECTOR;
GRANT ROLE C1_CONNECTOR TO USER <service account>;

-- SHOW USERS returns every column but "name" as NULL unless the session role owns
-- the user. There is no read-only alternative in Snowflake's access control model.
GRANT OWNERSHIP ON USER <user> TO ROLE C1_CONNECTOR COPY CURRENT GRANTS;

-- SHOW ROLES and SHOW GRANTS OF ROLE, per role C1 reviews or provisions.
GRANT OWNERSHIP ON ROLE <role> TO ROLE C1_CONNECTOR COPY CURRENT GRANTS;

-- Object-level inventory, metadata only: REFERENCES grants the ability to see an
-- object's structure but never its data. Omit all of this if you disable
-- "Sync databases and tables" (see Model C).
GRANT USAGE ON DATABASE <db> TO ROLE C1_CONNECTOR;
GRANT USAGE ON ALL SCHEMAS IN DATABASE <db> TO ROLE C1_CONNECTOR;
GRANT REFERENCES ON ALL TABLES IN DATABASE <db> TO ROLE C1_CONNECTOR;
GRANT REFERENCES ON ALL VIEWS IN DATABASE <db> TO ROLE C1_CONNECTOR;

-- SHOW INTEGRATIONS, per integration you want inventoried.
GRANT USAGE ON INTEGRATION <integration> TO ROLE C1_CONNECTOR;
```

<Warning>
**Under Model B, users the connector's role does not own sync with blank attributes.** Snowflake suppresses every `SHOW USERS` column but `name` for those users, so their login, email, and `TYPE` arrive empty. The connector detects this per user, logs a warning naming the user, and reports the account type as *unspecified* rather than guessing — a service account with a suppressed `TYPE` is no longer silently classified as a person. Either grant `OWNERSHIP` on every in-scope user or switch to Model A, where no per-user privilege is required.
</Warning>

<Note>
**Container-scoped `MANAGE GRANTS` is a third option that needs no connector change.** Snowflake supports granting `MANAGE GRANTS` on a single database or schema rather than on the account. If you want `SHOW`-path visibility across a bounded set of objects without account-wide privilege, grant it at the container level. See Snowflake's [container-level MANAGE GRANTS](https://docs.snowflake.com/en/user-guide/container-manage-grants-using) documentation.
</Note>

### Model C: users, roles, and grants only

If you do not want object-level privileges granted at all, turn **Sync databases and tables** off. The connector then syncs users, account roles, role grants, integrations, and licenses, and never issues `SHOW DATABASES`, `SHOW SCHEMAS`, `SHOW TABLES`, or the object-grant queries — so none of the object-level grants in Model A or B are needed.

This is different from **Excluded Databases**, which is a connector-side filter: it skips databases *after* the privileges have been granted and still requires every database you want skipped to be named. Model C removes the requirement entirely.

<Note>
Snowflake secrets are database-scoped. With **Sync databases and tables** off, the secret resource type is not synced even when **Sync secrets** is on; RSA public keys are user-scoped and are unaffected.
</Note>

### Privileges required for provisioning

Provisioning (creating, deleting, enabling, and disabling users, and issuing or revoking programmatic access tokens) runs as a dedicated **Write Role**, which defaults to Snowflake's `USERADMIN` system role. To avoid granting `USERADMIN` to the service account, set **Write Role** to a role of your own:

```sql
USE ROLE ACCOUNTADMIN;

CREATE ROLE IF NOT EXISTS C1_USER_LIFECYCLE;
GRANT ROLE C1_USER_LIFECYCLE TO USER <service account>;

GRANT CREATE USER ON ACCOUNT TO ROLE C1_USER_LIFECYCLE;            -- create / delete accounts
GRANT MODIFY ON USER <user> TO ROLE C1_USER_LIFECYCLE;             -- enable / disable accounts
GRANT MODIFY PROGRAMMATIC AUTHENTICATION METHODS ON USER <user>
  TO ROLE C1_USER_LIFECYCLE;                                       -- issue / revoke tokens
```

Grant-and-revoke of account roles runs as the session's default role, not the write role, and requires `OWNERSHIP` of the role being granted (or `MANAGE GRANTS`).

License sync reads `SHOW ORGANIZATION ACCOUNTS`, which runs as a dedicated **Organization Role** defaulting to `GLOBALORGADMIN`. Set **Organization Role** to a delegated organization role to avoid granting the top-level org admin role to the service account. License sync also counts users via `SELECT ... FROM SNOWFLAKE.ACCOUNT_USAGE.USERS`, so it needs `SNOWFLAKE.SECURITY_VIEWER` (or equivalent `SELECT`) and a running warehouse in **both** discovery modes. License sync is opt-in; if you do not enable it, none of this is needed.

<Note>
**Upgrade behavior.** **Write Role**, **Organization Role**, and **Discovery Mode** all default to exactly what the connector did before they existed (`USERADMIN`, `GLOBALORGADMIN`, and `show`), and **Sync databases and tables** defaults to on. An existing connector's behavior does not change until you change one of these.
</Note>

### Generate a private key and set the public key on a Snowflake user

<Steps>
<Step>
Generate an **unencrypted** private key in PEM format by running the following command: 

   ```bash
   openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out rsa_key.p8 -nocrypt
   ```
</Step>
<Step>
Next, use the private key to generate the public key. Run the following command:

   ```bash
   openssl rsa -in rsa_key.p8 -pubout -out rsa_key.pub
   ```
</Step>
<Step>
To enable public key authentication for a Snowflake user, execute the following `ALTER USER` command. A user with the `ACCOUNTADMIN` role must perform this operation:

   ```sql
   ALTER USER <SNOWFLAKEUSER> SET RSA_PUBLIC_KEY='MIIBIj...';
   ```

   **Tip:** When setting the `RSA_PUBLIC_KEY`, extract the key content between the `-----BEGIN PUBLIC KEY-----` and `-----END PUBLIC KEY-----` lines from your public key file. Do not include the header or footer. The key should be a single continuous string.

</Step>
<Step>
Carefully save the private key. 
</Step>
</Steps>

## Troubleshooting the Snowflake v2 connector

### 4xx errors

If you're seeing a `422 unprocessable entity` or `401 unauthorized` error in the logs, make sure that your service account has the `DEFAULT_WAREHOUSE`property, and that you've correctly looked up your Snowflake account identifier. 

### Connector fails when Snowflake IP allowlisting is enabled

If your Snowflake account has a [network policy](https://docs.snowflake.com/en/user-guide/network-policies) configured that restricts access by IP address, you must add C1's egress IP addresses to the allowlist. Otherwise, Snowflake will reject connections from the connector.

For **cloud-hosted connectors**, C1 manages the connector infrastructure. Add C1's connector egress IPs to your Snowflake network policy. See [C1 egress IP addresses](https://www.c1.ai/docs/product/admin/egress-ips) for the current list.

For **self-hosted connectors**, the connector runs on your own infrastructure, so you should add the outbound IP addresses of your own environment instead.

### Validation fails with "no user attributes are visible to the connector's role"

Snowflake returns every `SHOW USERS` column but `name` as NULL — including the `TYPE` column used to detect service accounts — unless the session role owns the user or holds account-level `MANAGE GRANTS`. When *no* sampled user's attributes are readable, the connector fails startup rather than syncing users with blank attributes. Fix it with any one of the following, in increasing order of privilege:

1. **Grant `OWNERSHIP` on each in-scope user** (Model B):
   ```sql
   USE ROLE ACCOUNTADMIN;
   GRANT OWNERSHIP ON USER <user> TO ROLE <connector role> COPY CURRENT GRANTS;
   ```
2. **Switch to ACCOUNT_USAGE discovery** (Model A), which has no per-user privilege requirement at all. Set **Discovery Mode** to `account_usage` and grant:
   ```sql
   USE ROLE ACCOUNTADMIN;
   GRANT DATABASE ROLE SNOWFLAKE.SECURITY_VIEWER TO ROLE <connector role>;
   ```
3. **Grant account-level `MANAGE GRANTS`.** This works, but it is an account-wide, self-escalating standing privilege; prefer option 1 or 2.
   ```sql
   USE ROLE ACCOUNTADMIN;
   GRANT MANAGE GRANTS ON ACCOUNT TO ROLE <connector role>;
   ```

Also confirm the service account actually has a role **granted** to it. A `DEFAULT_ROLE` that was set but never granted produces this exact signature.

### Some users sync with a blank login, email, and account type

This is the partially visible case under `show` discovery: the connector's role owns some in-scope users but not others. Startup succeeds, because a tenant may legitimately hand over only a subset of users, but each affected user is logged as a warning naming the user, and its account type is reported as *unspecified* rather than guessed as human.

Grant `OWNERSHIP` on the named users, or switch **Discovery Mode** to `account_usage`, to sync them fully.

### ACCOUNT_USAGE discovery fails with "SNOWFLAKE.ACCOUNT_USAGE is not readable"

The connector's role cannot read the `ACCOUNT_USAGE` views. Snowflake reports this as a SQL compilation error (`Object 'SNOWFLAKE.ACCOUNT_USAGE.USERS' does not exist or not authorized`) rather than as a privilege error. Check both of the following:

- The viewer database roles are granted: `SNOWFLAKE.SECURITY_VIEWER` for users, roles, and grants, and `SNOWFLAKE.OBJECT_VIEWER` for databases, schemas, and tables.
- The service account has `USAGE` on a warehouse that can resume. `ACCOUNT_USAGE` reads are `SELECT` statements and need compute, unlike the `SHOW` commands the default discovery mode uses.

### ACCOUNT_USAGE discovery is missing a recently created user, role, or table

`ACCOUNT_USAGE` views lag the live account by roughly 90 minutes to 3 hours depending on the view. This is expected. If you need live data, use `show` discovery instead — see [Choose a privilege model](#choose-a-privilege-model).
